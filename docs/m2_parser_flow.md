# M2 parser flow and run boundaries

This describes the proposed operating flow; the full 20,000-paper Colab run and its interruption test have not yet been performed.

1. Mount Drive and fix the run ID, code revision, five M1 checkpoint identities, recovery journal, parser settings and output location. Use a new run ID when an input or setting changes.
2. Restore the corpus and version journal of the five M1 partitions to local Colab storage, checking checkpoint hashes with bounded parallel Drive reads. M1 telemetry is not copied by this M2-only restore. Keep the recovery output as a separate input root; never overlay its files on the restored M1 corpus. Check accessible space and record setup time.
3. Start the parser with the five corpus roots and `--bbl-recovery-dir` pointing to the recovery run. Before parsing, it reconciles the candidate list, journal and summary for the full run, verifies corpus content and every recorded recovered BBL by SHA-256, verifies paper/version mapping and pins input identities for resume. It checks the BBL hash again when reading the exact bytes used by the parser. These checks run within the measured parser process; Drive restore is separate setup. The current `input_size` metric measures corpus roots; BBL files read from the separate Drive root are excluded and their storage must be reported separately.
4. For each paper, process each available version in order. Gather the root TeX and transitive includes, extract text structure, normalize and build the hierarchy. If a version has no TeX, record its empty status; if its folder is missing or parsing fails, record that separately.
5. For references, parse the TeX bibliography and named `.bib` files first. When no entries are obtained, read the BBLs indexed for that exact paper/version from the separate recovery root. A recovered file is not necessarily parseable, and a BBL that is read does not imply references were successfully extracted. A simultaneous local and external BBL is reported as a conflict.
6. Deduplicate references and text across versions of that paper; write `elements`, `hierarchy` and `bibtex` to a committed Parquet shard and append its journal record. Workers receive only the BBL paths for their assigned paper.
7. Periodically sync a journal snapshot and all referenced shards to Drive with SHA-256 checks; report files are copied only after the benchmark process exits. On resume, first confirm any previous runtime has stopped, restore a consistent snapshot, re-check input identities and continue from committed papers. Session state flags interrupted or unmeasured work; incomplete wall time and sampled peaks are lower bounds, not a completed end-to-end measurement. Sync verification competes with the parser for resources and its cost affects wall time.
8. Before starting the full run, exercise these steps in a separate Colab smoke run containing BBL, multi-version, no-TeX and unavailable examples. Interrupt and resume it; reconcile outputs, hashes, identities and session accounting. An offline test is not evidence that this Colab/Drive smoke succeeded.

Recovery requests and storage are separate from the M1 crawl benchmark. S3 v1 metadata remains an inference from the snapshot/bundle evidence; the recovered arXiv v1 BBL is not evidence that the S3 archive is byte-identical.
